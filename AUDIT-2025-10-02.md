# Codex Roster — Audit Report (2025-10-02)

Scope: `src/` (Rust, ~25k LOC) + `macos/NextAccount/Sources/` (SwiftUI, ~14k LOC).
Mode: source-first review; no runtime probing, no network calls against live endpoints.

Threat model (actual): the app's whole job is to swap `~/.codex/auth.json`,
`~/.claude` credentials, and provider secrets for the **same local user**.
Relevant boundaries:

1. **Local attacker / other processes under the same UID** — world-readable
   secret files, plaintext keys, `/tmp` staging, env-var-controlled binaries.
2. **Supply chain** — `npx --yes` downloads and executes code; GitHub updater
   replaces the app bundle; update metadata fetched over TLS.
3. **Untrusted input** — encrypted backups imported from disk, session rollout
   files authored by Codex, GitHub API JSON.
4. **Concurrency / crash-safety** — two roster processes (GUI + CLI + tray)
   mutating the same auth files; partial writes.

Below are the findings that survive a boundary test. Severity follows the
anchors: **high** = defeats an explicit control with real consequences;
**medium** = real boundary violation with limited blast radius; **low** =
disclosure / minimal gain; **info** = useful prerequisite.

---

## High

### H1 — `npx --yes` downloads and executes arbitrary code (supply chain)

`src/app/usage_refresh.rs:53` and `src/cli.rs:1388` run:

```rust
std::process::Command::new("npx")
    .args(["--yes", "@vibe-cafe/vibe-usage", "sync"])
```

`--yes` tells `npx` to silently download the package if absent — no pin, no
checksum, no lockfile. The binary inherits the user's full PATH. If the
`vibe-cafe` npm account is compromised (or DNS/registry poisoning), the
auto-refresh worker runs attacker code **every poll interval** on every
configured machine.

*Boundary*: registry content → arbitrary code execution as the local user.
*Smallest fix*: pin a specific version (`@vibe-cafe/vibe-usage@x.y.z`), or
ship the collector in-process (it's a plain HTTPS GET to `vibecafe.ai`).
If pinning, verify in code that the resolved spec is the pinned version.

### H2 — `auth.json` restore follows symlinks and is not atomic

`src/codex.rs:539` (`stage_and_restore`) restores credentials with
`fs::remove_file(live)` → `fs::copy(staged → live)`. Two problems:

1. **Symlink following**: `fs::copy` writes *through* a symlink at the
   destination rather than replacing it. If a same-UID attacker (or a
   misbehaving tool) replaces `~/.codex/auth.json` with a symlink to a file
   they control, Roster copies the decrypted OAuth refresh-token bytes into
   that file — quiet exfiltration of the credential onto an attacker-chosen
   inode. No `lstat`/no-follow check exists anywhere on the restore path.
2. **Non-atomic**: between `remove_file` and `copy`, `auth.json` simply does
   not exist; a crash in that window leaves Codex logged out (the `.cas-backup-*`
   dir mitigates this, but only via manual recovery). A concurrent reader
   (Desktop app-server, `codex` CLI) sees a missing or half-written file.

Note: `fs::copy` does preserve the staged file's `0600` mode on Unix, so
permissions are fine — the defect is symlink-following and non-atomicity, not
mode downgrade.

*Boundary*: same-UID attacker → credential bytes written to attacker-controlled
path; crash/mid-swap reader → missing or truncated auth.
*Fix*: `rename` the staged file over `live_path` (atomic, replaces any symlink
rather than following it). This single change fixes both halves and subsumes
M6's atomicity point.

### H3 — Self-update script executes from a predictable, non-rooted path

`macos/.../GitHubUpdater.swift:98-141` writes `install-update.sh` into
`FileManager.default.temporaryDirectory` (which is `$TMPDIR`, often a
per-user path but still attacker-visible on multi-user systems), then runs it
via `/bin/sh`. The script moves the downloaded `.app` bundle into
`/Applications` — a privilege boundary — with no code-signing verification of
the downloaded bundle, only a SHA-256 comparison against the GitHub API's
self-reported `digest` field.

*Boundary*: GitHub release metadata → code execution with the ability to
replace an installed app. The digest check is genuine but trusts the release
manifest; a compromised GitHub release (or a malicious asset with a matching
digest claimed in the API) installs cleanly. More importantly, the helper
script itself lives in a directory another same-UID process can replace
between write and exec (TOCTOU).

*Fix*: verify the downloaded `.app`'s code signature matches the current
signing identity (`codesign -dv --verbose` / `SecCodeCheckValidity`) before
installing. Write the helper script into `~/Library/Application Support/…`
(dir mode `0700`) instead of `$TMPDIR`. Consider Sparkle framework.

## Medium

### M1 — `security -i` writes credentials through a shell-string on stdin

`src/provider/claude_keychain.rs:106-125` builds a text command

```
add-generic-password -U -a "acct" -s "svc" -X 68656c6c6f2d736563726574\n
```

and pipes it into `/usr/bin/security -i`. `security -i` is an **interactive
shell**: it parses the line, runs its own tokenizer, and executes the result.
`quote()` handles `"` and `\` but not newlines, `$`, backticks, `;`, `!`,
or other characters `security -i` may interpret. A `$USER`/`$USERNAME` or
service string containing a metacharacter could escape the intended command.

Currently `account_name()` is derived from `USER`/`USERNAME` env vars —
attacker-influenceable in some contexts (sudo env, subshells). The
`claude_code-user` fallback means a forged `USER` value could target a
different keychain account.

*Fix*: prefer the direct argv path for every call (`add-generic-password`
argv form already exists in the `else` branch — the `use_stdin` threshold is
arbitrary); drop the `-i` mode entirely, or strictly validate `account` /
`service` against `[A-Za-z0-9._-]+`.

### M2 — `CODEX_ROSTER_CLI_PATH` env-var hijacks all GUI shell-outs

`AccountStore.swift:3156` resolves the CLI via `CODEX_ROSTER_CLI_PATH`,
`ACCOUNT_HUB_CLI_PATH`, `NEXT_ACCOUNT_CLI_PATH`, finally falling back to
`/usr/bin/env codex-roster`. Anything that can set an env var on the GUI
process (`.zshenv`, `launchctl setenv`, a compromised parent app, or a
dev-machine shell profile) silently substitutes the privileged binary that
reads/writes keychain entries and `~/.codex`.

*Fix*: prefer the bundled executable (`Bundle.main.url(forAuxiliaryExecutable:)`)
as the *primary* source; env overrides should be opt-in via a developer flag,
and validate the resolved binary (code signature / path prefix under
`/Applications` or the bundle).

### M3 — Plaintext snapshot encryption key lives in a regular file

`src/backup.rs:185-233` writes the age-scrypt password to
`~/Library/Application Support/com.codexroster.codex-roster/keys/*.key` as
raw text `0600`. It is only migrated back to Keychain "best-effort".

Any local backup tool (Time Machine, iCloud Drive, `rsync`) now copies the
key file along with the encrypted snapshots — completely defeating the
encryption-at-rest goal. The code comments acknowledge the Keychain-binding
problem (orphaned on ad-hoc signature change), but the plaintext fallback
moves the secret out of the TCC/keychain trust boundary into the regular
filesystem.

*Fix*: at minimum, store the file as `data:` bytes, mark it `chflags hidden`
+ `NSURLIsExcludedFromBackupKey`, and on macOS prefer `kSecAttrAccessible`
with `ThisDeviceOnly`. Document the tradeoff — current comment says
"file is now the source of truth" without flagging the backup leakage.

### M4 — Legacy data migration follows a user-controlled rename

`src/env.rs:47-69` `migrate_legacy_data_dir` picks the *first existing* dir
from a fixed list and `fs::rename`s it into `~/Library/Application Support/
com.codexroster.codex-roster`. Because the legacy apps also wrote into the
same `~/Library/Application Support/{accounthub,nextaccount,nextide}` paths,
a same-UID attacker who drops a symlink or a file at one of those legacy
paths before first launch gets it adopted as the app's data dir — and Roster
then happily reads "saved accounts" from attacker content.

*Fix*: verify each legacy candidate `lstat`s as a real directory (not a
symlink), owned by the current uid, before renaming; or migrate files rather
than the directory inode.

### M5 — `status.openai.com` / `codex-resets.com` results shown to user unfiltered

`src/openai_status.rs` and `src/reset_tracker.rs` fetch third-party JSON and
print summaries into the TUI/GUI. `codex-resets.com` is a **third-party site**
(not OpenAI). Its `resets` feed (tweet URLs, messages) is rendered as trusted
status content next to account data. `reset_tracker.rs:204` builds `x.com`
status URLs from arbitrary `id` digits in the API response — a malicious
payload could inject a phishing link into the UI.

*Fix*: whitelist/validate IDs (`^\d{15,25}$`), render sources as
`[external]` labels in UI, and never pass fetched strings into URL-opening
code paths without validation.

### M6 — TOCTOU / lock gaps around `auth.json` swap

`src/codex.rs:stage_and_restore` writes staged files, removes `live_path`,
then `fs::copy`s into place — a non-atomic sequence where a crashed process
leaves `auth.json` absent until rollback runs. The `OperationLock` /
`AuthLock` cover *roster* processes, but nothing blocks Codex itself (or the
user's shell) from opening `auth.json` mid-swap. `verify_live_snapshot_once`
catches *content* drift, not readers.

`processes_blocking_activation` does detect running `codex` processes, but
`is_force_skippable_process` treats `app-server`/`mcp` as background and
`--force` skips them — even though a Desktop app-server holds an open handle
to the file being replaced.

*Fix*: write to `auth.json.tmp` + `rename` into place (atomic within the
same filesystem); treat `app-server` as blocking when it has the file open
(`lsof` check), not just by role name.

## Low / Informational

### L1 — `auth-debug.log` writes token fingerprints with no rotation

`src/codex.rs:auth_debug` appends to `auth-debug.log` unbounded; opt-in, so
low risk — but the file isn't `0600` and has no size cap. Small: set
permissions + rotate at e.g. 1MB.

### L2 — `session-resume.log` (Swift) same issue — `try? data.write(to:)`
creates with default perms; content includes session paths + timestamps.

### L3 — `vibe-usage` config is trusted on read, with plaintext `api_key`

`src/vibe_usage.rs` reads `~/.vibe-usage/config.json` without permission
check — a `0644` file leaks the bearer key to any local reader.

### L4 — `ureq` calls don't pin TLS roots or set `Connection: close`

All API calls use system TLS; that's acceptable for this threat model but
`timeout_global(5s)` everywhere means a hanging endpoint stalls the TUI for
5s×retry — UX issue more than security.

### L5 — Unwrap density

781 `unwrap()`/`expect()` outside tests, concentrated in `session_resume.rs`
(62) and `app/service.rs`. Most are on `Path::to_str()` (non-UTF8 home paths)
and locks. Real-world panic surface is modest but non-zero — see Quality.

### L6 — `pkcs8` / `age` versions pinned, but `ureq` 3.x is young

`ureq 3.1.2` is a recent major release; consider `cargo audit` in CI.

## What was *not* found

- **No credential exfiltration paths** — all `ureq` calls go to fixed HTTPS
  endpoints (openai, anthropic, cursor, grok, github, vibecafe opt-in).
- **No unsafe Rust** in `src/`.
- **Encryption is well-formed** — age with scrypt, size caps on decrypt,
  magic-byte versioning, key separation between backup (`automatic-backup-key`)
  and local snapshots (`local-snapshot-key`). The rotating-key-file design
  (M3) is a deliberate tradeoff, not a bug.
- **Lock discipline is mostly right** — `AuthLock` correctly covers the
  read→refresh→write transaction; refresh tokens are treated as single-use.
- **Recovery paths are thoughtful** — `.tmp-*`/`.bak-*` recovery, refuses to
  overwrite ≥2 accounts with empty index, automatic backup of metadata.

---

## Recommended fix order

1. **H1** — pin or remove `npx --yes` (one-line supply-chain fix).
2. **H2** — atomic `rename` (not `fs::copy`) for the `auth.json` swap; also closes M6.
3. **H3** — code-signing verification on the downloaded update bundle.
4. **M2** — bundled CLI first; env override behind a flag.
5. **M3** — exclude the key file from backups, document the tradeoff.
6. **M6** — atomic rename for `auth.json` swap; treat Desktop `app-server` as
   blocking when it holds the file.
7. M1, M4, M5 — hardening.
8. Q3 — index/snapshot ordering.

*Audit performed read-only. No dynamic execution. Some findings (M1, M4)
depend on OS-level behavior (keychain prompts, `security -i` grammar,
`lstat` semantics) that a runtime sandbox pass could confirm — flagged
here as "needs validation" within a fuller workflow.*
